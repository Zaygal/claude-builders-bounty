# CLAUDE.md

> Context for Claude Code working in this repository.
> A Next.js 15 (App Router) + SQLite SaaS. Everything here is a decision,
> not a suggestion — each rule names its reason so you can override it
> deliberately instead of accidentally.

## Stack & versions (do not drift)

- **Next.js 15.x** (App Router) on **React 19**, **TypeScript 5** in `strict`
- **SQLite** via `better-sqlite3` (synchronous, single-instance). `@libsql/client` (Turso) is the managed swap — keep every DB call behind the Drizzle client so the swap is a one-file change.
- **Drizzle ORM** + `drizzle-kit` for schema and migrations (thin enough that the SQL stays visible).
- **Better Auth** for authentication (email/password + OAuth).
- **Tailwind CSS v4** + **shadcn/ui** for the UI layer.
- **Node 20+ LTS**, **npm** as the package manager.

*Why this stack:* naming it up front removes the "which ORM / which auth / which DB" questions that otherwise stall every greenfield session. better-sqlite3 is the fastest single-instance choice; Drizzle keeps queries greppable instead of hiding them in an ORM.

## Folder structure

```
src/
  app/              # routes ONLY — one folder per route
    (auth)/         #   route group: public auth pages
    (dashboard)/    #   route group: authenticated app shell
    api/            #   route handlers
  components/
    ui/             #   shadcn/ui primitives (generated — do not hand-edit)
    shared/         #   cross-route server components
    features/       #   one folder per feature
  lib/
    db/             #   drizzle client, schema, migrations
      schema/       #   one file per table
  server/           # server actions + queries (the RPC surface)
  hooks/            # client hooks only
  types/            # shared TS types (zod-inferred where possible)
```

- `app/` holds routes and nothing else. Business logic lives in `server/` or `lib/`. *Reason: App Router files are painful to unit test; thin routes keep logic testable and reusable.*
- `components/features/<feature>/` — one folder per feature. *Reason: a flat `components/` dir becomes a junk drawer the moment a second feature lands.*
- `db/schema/` — one file per table. *Reason: a single `schema.ts` becomes unmergeable in a team.*

## SQL / migration conventions

- **Migrations are append-only.** Never edit a migration that has been applied to any environment. *Reason: editing history desyncs dev/staging/prod; the fix is always a new migration.*
- **One migration per logical change**, generated by `npm run db:generate` from the Drizzle schema. Hand-write the numbered SQL only when you must.
- **Every table:** `id INTEGER PRIMARY KEY AUTOINCREMENT`, `created_at` and `updated_at` as `INTEGER` (unixepoch, `DEFAULT (unixepoch())`). `updated_at` is updated explicitly by the data layer in one shared helper, not by a trigger. snake_case, plural table names. *Reason: visible, greppable updates beat hidden trigger magic; unixepoch avoids timezone-parse bugs.*
- **Pragmas:** foreign keys ON, WAL mode, `busy_timeout=5000`. *Reason: WAL gives concurrent reads during writes; busy_timeout prevents "database is locked" in multi-process dev.*
- **All SQL goes through the Drizzle client** in `lib/db/`. No raw queries in route handlers or components. *Reason: one choke point for transactions, logging, and the better-sqlite3→Turso swap.*
- **No `SELECT *`.** Select explicit columns. *Reason: payload size, and an accidental PII/column leak when the schema grows.*

## Component patterns

- **Server components by default.** Add `'use client'` only at the leaf where interactivity begins. *Reason: smaller client bundles, less hydration cost, and the DB stays server-side.*
- **Fetch data in the server component, a route handler, or a server action — never a client component.** *Reason: the client cannot hold a SQLite connection, and a leaked query leaks the shape of your schema.*
- **Mutations go through server actions in `server/`.** Validate input with zod before touching the DB.
- **One component = one job.** If a component passes ~200 lines or takes more than 3 object props, split it. *Reason: large components are where prop-drilling and stale-closure bugs breed.*

## Dev commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` — production build; run before every PR
- `npm run lint` / `npm run lint:fix` — ESLint + Prettier
- `npm run typecheck` — `tsc --noEmit` (the real gate; passing lint is not enough)
- `npm run db:generate` — generate a migration from schema changes
- `npm run db:migrate` — apply pending migrations
- `npm run db:studio` — drizzle-kit studio (browse data locally)
- `npm run db:push` — dev-only schema sync (never in staging/prod)

## What we don't do (and why)

- **No client-side DB access.** SQLite runs server-side only. *Reason: it cannot run in the browser, and exposing it leaks the whole database.*
- **No editing applied migrations.** Always a new migration. *Reason: see "append-only" above.*
- **No `any`, no `@ts-ignore`.** *Reason: the type system is the first test; silencing it hides the bug, it doesn't remove it.*
- **No ORM "magic" that hides the SQL.** Drizzle keeps queries visible — don't wrap it in abstractions that obscure the `WHERE`. *Reason: SQLite performance problems are invisible until you can see the actual query.*
- **No secrets or server-only imports in client components.** *Reason: they ship in the JS bundle.*
- **No `'use client'` on a page/layout just to "make it work."** Find the real boundary. *Reason: turning a whole page client-side discards the performance you adopted the App Router for.*
- **No long-lived transactions or write locks held across network calls.** *Reason: SQLite is single-writer; blocking it blocks every request.*
